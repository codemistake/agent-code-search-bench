# agent-code-search-bench

Замер инструментов навигации по коду для агента: сколько стоит **весь ответ на
вопрос**, а не один вызов поиска.

Вендоры в этой категории меряют экономию токенов на вызов: «на 98% меньше, чем
grep+read». Счёт приходит не за вызов, а за сессию. Если инструмент отдаёт
компактный ответ, но агент делает вдвое больше ходов, а каждый ход шлёт контекст
заново, сессия дорожает при формально меньшем поиске.

Здесь единица замера — вопрос целиком: все токены всех ходов, число ходов, число
вызовов инструментов, время до ответа и попадание в правильные файлы.

Результаты одного прогона: [RESULTS.md](RESULTS.md).

## Что сравнивается

Шесть плеч. Плечо — это то, **чем** агент ищет по репозиторию. Модель, корпус,
набор вопросов и системный промпт у всех одинаковые.

| Плечо | Инструмент | Как работает |
|---|---|---|
| `baseline` | встроенные grep, glob, read | точка отсчёта |
| `ast-grep` | [ast-grep](https://github.com/ast-grep/ast-grep) | поиск по AST-шаблонам, CLI |
| `semble` | [semble](https://github.com/MinishLab/semble) | Model2Vec + BM25, CLI |
| `repomix` | [repomix](https://github.com/yamadashy/repomix) | весь репозиторий одним сжатым файлом |
| `codanna` | [codanna](https://github.com/bartolli/codanna) | граф символов, MCP-сервер |
| `codebase-memory` | [codebase-memory-mcp](https://github.com/DeusData/codebase-memory-mcp) | граф tree-sitter, MCP-сервер |

## Как устроен замер

**Вопросы с проверяемым эталоном.** Для каждого вопроса заранее известен набор
файлов, которые обязаны быть в ответе, и строки, которые обязаны в нём
прозвучать. Эталон собирается по самому репозиторию (`rg -l`, `rg "export
function X"`) и проверяется руками до прогона. Метрики: `recall` — доля
эталонных файлов, названных в ответе; `exact` — прогон, где названы все файлы и
все строки.

Никакого LLM-судьи: ответ либо содержит нужный путь, либо нет.

**Четыре типа вопросов.** `lexical` — точная строка или константа.
`structural` — «кто вызывает X», «что сломается, если поменять Y».
`semantic` — вопрос своими словами, без имён из кода. `hard` — то же, но ответ
требует нескольких переходов по графу вызовов или чтения тела функции.

**Токены берутся с сервера, а не оцениваются.** После каждого прогона харнесс
делает `opencode2 export <session>` и суммирует `tokens.input` и `tokens.output`
по всем ходам. Именно по всем: каждый ход шлёт контекст заново, и платится
сумма, а не input последнего хода.

**Плечо принуждено пользоваться своим инструментом.** Одной инструкции в
`AGENTS.md` мало — модель читает «используй ast-grep» и всё равно зовёт grep.
Инструменты закрываются правами агента:

- `baseline` — всё разрешено;
- `ast-grep`, `semble`, `repomix` — закрыты `grep` и `glob`, закрыт `subagent`
  и закрыт `shell` по образцу команды (`*grep*`, `*rg *`, `*findstr*`,
  `*Select-String*`);
- `codanna`, `codebase-memory` — оставлены только `read`, `list` и `execute`.

Каждый обходной путь в этом списке появился после того, как агент им
воспользовался: сначала звал бинарь `grep` из шелла в обход запрета инструмента,
потом `rg`, потом перепоручал поиск субагенту `explore`.

**Автоконтроль заражения.** Агент умеет ходить по каталогам вверх и однажды
дошёл до файла с вопросами. Каждый прогон проверяется на признаки того, что
агент видел эталон; заражённые помечаются `tainted: true` и в отчёт не идут.

## Что понадобится

- Node.js 22 или новее
- [opencode](https://opencode.ai) v2 (бинарь `opencode2`) с настроенным провайдером модели
- сами инструменты — ставятся под те плечи, которые собираетесь гонять

```bash
npm i -g @ast-grep/cli repomix
uv tool install semble
cargo install codanna --locked
```

`codanna` собирается долго и требует много памяти при сборке; на слабой машине
берите готовый бинарь из [релизов](https://github.com/bartolli/codanna/releases).
`codebase-memory-mcp` ставится из [своих релизов](https://github.com/DeusData/codebase-memory-mcp/releases).

## Как воспроизвести

### 1. Положите корпус в отдельное дерево

Каталог с репозиторием-корпусом не должен соседствовать с харнессом: агент
поднимается по каталогам вверх и находит файл с ответами.

```bash
mkdir -p /c/bench-arena/repo
git -C /path/to/your/repo archive HEAD | tar -x -C /c/bench-arena/repo
```

Корпус должен быть git-репозиторием — по этому признаку opencode определяет
корень проекта.

```bash
cd /c/bench-arena/repo && git init -q && git add -A && git commit -qm corpus
```

### 2. Соберите набор вопросов

Скопируйте [`questions.example.json`](questions.example.json) в
`questions.json` и напишите вопросы по своему репозиторию. Эталон **проверьте
до прогона**, иначе замеряете не инструменты, а свои опечатки:

```bash
rg -l "\bwriteAtomic\b" src/            # кто импортирует
rg -n "export function writeAtomic" src/ # где определена
```

Поля записи:

- `id` — короткий идентификатор, попадает в отчёт;
- `kind` — `lexical`, `structural`, `semantic` или `hard`;
- `q` — сам вопрос;
- `must_files` — пути, которые обязаны быть в ответе;
- `must_text` — строки, которые обязаны прозвучать (URL, версия, имя функции).

### 3. Запустите

```bash
BENCH_CORPUS='C:\bench-arena\repo' BENCH_MODEL='your/model' node bench.mjs --repeats 2
```

Плечо `codebase-memory` по умолчанию выключено и включается флагом
`--with-cbm` — см. «Осторожно» ниже.

Отдельные плечи:

```bash
node bench.mjs --arms baseline,semble --repeats 3
```

Переменные окружения:

| | |
|---|---|
| `BENCH_CORPUS` | путь к корпусу; обязателен, если корпус не в `../arena/repo` |
| `BENCH_MODEL` | идентификатор модели в формате `provider/model` |
| `BENCH_BIN` | дополнительные каталоги с бинарями инструментов |

### 4. Соберите отчёт

```bash
node report.mjs > report.md
```

Сырьё остаётся в `results.jsonl`, по строке на прогон: токены, ходы, вызовы,
имена вызванных инструментов, найденные и пропущенные файлы, флаг заражения.

## Грабли, на которые мы наступили

Всё перечисленное сначала испортило прогон и только потом было исправлено.
Если запускаете у себя, они ваши тоже.

**Рабочий каталог агента задаётся переменной `PWD`.** Не опцией `cwd` у
`spawn`, не `cd` внутри команды, не `process.chdir` и не каталогом файла
`OPENCODE_CONFIG` — проверено всеми четырьмя способами. Git Bash выставляет
`PWD` при `cd`, node при `process.chdir` его не обновляет, а opencode читает
именно окружение. Пока это не было починено, агент работал в каталоге харнесса
и читал оттуда правильные ответы.

**Фоновый сервис opencode не перечитывает MCP-серверы из проектного конфига.**
`opencode2 mcp list` показывал новый сервер как `pending` до конца прогона, а
плечо всё это время молча измеряло голый grep. Работает только связка: свой
конфиг через `OPENCODE_CONFIG` плюс `--standalone`.

**MCP-инструменты в opencode v2 видны лишь через Code Mode.** Прямыми
инструментами они не появляются; агент зовёт их изнутри `execute` как
`tools["server-name"].method({...})`.

**`opencode2 run` без закрытого stdin висит вечно.** Ждёт EOF.

**`p.kill()` при `shell: true` убивает `cmd.exe`, а не процесс под ним.**
Осиротевшие серверы `--standalone` копятся за прогон и в какой-то момент вешают
харнесс. Нужен `taskkill /T /F`.

**Аргументы уезжают через `cmd.exe`.** Переносы строк и кавычки в промпте он
коверкает молча: сессия создаётся, сообщение в неё не уходит, прогон
завершается за секунды с нулём токенов.

## Осторожно

Плечо `codebase-memory` включается явным флагом `--with-cbm`. У инструмента на
момент замера были открыты
[#2045](https://github.com/DeusData/codebase-memory-mcp/issues/2045) —
инсталлятор на Windows 11 стёр пользователю переменные PATH — и
[#2021](https://github.com/DeusData/codebase-memory-mcp/issues/2021) — BSOD
`0x3B` в `Ntfs.sys`. В этом замере бинарь брался распакованным из релиза, с
проверкой SHA256, без запуска их установщика; PATH был выгружен в `.reg` до
начала. BSOD не воспроизвёлся.

Инструмент при старте резервирует половину оперативной памяти
(`mem.init budget_mb=32623` при 64 ГБ).

## Что здесь не так

- Один корпус, один язык, одна модель, Windows.
- `N=2` на вопрос: доверительных интервалов нет.
- Корпус в 385 файлов почти не различает инструменты по recall — у четырёх
  плеч он выше 96%.
- Плечо `ast-grep` свой бинарь звало редко даже с закрытым grep.

Подробнее — в разделе «Что этими числами не измерено» в [RESULTS.md](RESULTS.md).
